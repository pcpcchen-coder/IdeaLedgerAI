## 架構

背景負責**所有決策**，平台分頁裡的 content script 只是**執行者**（RPC）。這樣節流、退避、狀態都在一處，且可用假時鐘測試。

**平台開放：** 要巡檢哪些平台、各自的網域，一律來自 `registeredPlatforms()`（建置時由 `src/adapters/*/platform.json` 產生），不得在背景程式寫死平台清單。新增一個平台資料夾後，排程、分頁管理、狀態儲存都要自動涵蓋它。

```
bg/index.js       註冊 alarms、訊息處理（含「立即巡檢」）
bg/scheduler.js   每 30 分鐘 + 0–5 分隨機延遲；同一時間只跑一輪
bg/tabs.js        ensureTab(platform)：找現有分頁 → 沒有就開釘選、非作用中分頁 → 被休眠就重新載入並等待完成
bg/rpc.js         callTab(tabId, op, args)，逾時 30 秒
bg/round.js       單一平台一輪的流程（見下）
bg/state.js       chrome.storage.local 每平台：watermark、backfillQueue、backoffLevel、backoffUntil、status、lastRun
bg/collector.js   postConversation、postSweepRun、getWatermark；逾時 10 秒
lib/planner.js    純函式：決定這輪要抓哪些對話、水位線怎麼前移
lib/throttle.js   每次 RPC 之間 ≥3 秒（加 0–1 秒隨機）
lib/backoff.js    429／403 → 1→2→4→8 小時（上限 8）；成功一輪歸零
content/sweeper.js  RPC 路由：checkLogin、listUpdated、getConversation → 對應 adapter
```

## 單一平台一輪（round.js）

1. 在退避期內 → 跳過，狀態維持「退避中」。
2. `ensureTab` → `checkLogin`；失敗 → 狀態「需重新登入」，結束。
3. **一般模式**（watermark 有值）：逐頁 `listUpdated`，直到項目 `updated_at ≤ watermark` 或沒有下一頁。
4. **回填模式**（watermark 為空且無 backfillQueue）：列出全部歷史（同樣節流），依 `updated_at` 由舊到新存入 backfillQueue。之後每輪從佇列取。（2026-10-15 T08 起改為由新到舊，最近的對話先進資料庫。）
5. `planner`：排除 10 分鐘內更新的對話；由舊到新排序；取前 30 篇。
6. 逐篇 `getConversation` → `postConversation`；**每成功一篇就把 watermark 存為該篇的 `updated_at`**（服務程式可能隨時被瀏覽器終止，下一輪要能接續）。
7. collector 連不上 → 中止本輪、不前移水位線，狀態「collector 離線」。
8. 結束時 `postSweepRun`。

- 與工單描述的差異：
  - 時間一律用 `Date.parse` 比較，不用字串比較（各平台 ISO 格式的小數位數不同）。
  - 回填佇列只放已靜止的對話；還在聊的對話比佇列中最新的還新，回填結束後由一般模式接手，不會漏。
  - 回填中不重新列清單，直接從佇列取。
  - 新增 `CollectorRejected`（401／422）與 `reviveError`；未設定 token 時整輪略過，不會先打平台再失敗。
  - `sweep_run` 狀態沿用 T03 的五種；`collector_offline` 只存在擴充本地狀態（送不出去）。
- 尚待 T07：`config` 由設定頁編輯、「立即巡檢」按鈕（背景已支援 `sweepNow`、`getStatus` 訊息）、擴充圖示燈號。
